Where this stands

Phase A shipped the date foundation and the data layer. Everything since has been planning, three grilling rounds, and a read of the delivery path — which is where the release changed shape.

The plan began as one feature: a calendar that lands first and lets a volunteer plan a day. Auditing how that feature would actually reach three remote NGOs surfaced seven defects that already exist in the shipped app. None were caused by the calendar. All of them sit in its blast radius, and two of them mean an NGO can lose data today.

That is why this release is large. It is not ceremony — it is repair.

02

The defect ledger

Each of these was read in source, not inferred. Ordered by what they cost if left alone.

The app says a backup was saved when no file exists

saveFile() fails all three of its paths on Android — no Web Share API in a WebView, @capacitor/share was never installed, no download listener registered, and blob URLs can't reach Android's DownloadManager. It then returns success, and the UI displays "Backup file downloaded. Store it safely." This manufactures false confidence in a backup that does not exist.

helpers.js:149 · MainActivity.java · fixed by F0, first

The "full" backup is not full

The payload is stamped backupType: 'full' but omits occasions and campaigns — every custom occasion and every campaign the NGO ever built. Restore after a reinstall loses them silently.

SyncManager.js:468 · fixed by R0.1

A full-backup file cannot be restored

Only the paste route rebuilds state. A backup file always goes through SyncService.merge(), which reads three collections and drops six — reporting success. The safest-looking action a careful user can take is the one that loses their data.

SyncManager.js:523 vs :547 · fixed by R0.3

Festivals fire on the wrong day, forever

Occasion stores only month and day, but Indian festivals follow lunar calendars and move every year. Not one seeded occasion is a festival — all five are fixed civic dates. Two code comments tell users they may add "movable festivals", which is how a wrong-day Diwali greeting reaches hundreds of supporters in the NGO's name.

Occasion.js:3 · constants.js:155 · fixed by O1–O4

One un-backed-up file controls every future upgrade

There is no signingConfig anywhere in android/, so release builds are unsigned and unusable. The only installable artifact is the debug APK, signed by ~/.android/debug.keystore on one laptop. Lose that 2.6 KB file and every device must be uninstalled — destroying its data — to take any future release.

app/build.gradle · fixed by R1.2, R1.3

CI publishes an APK that cannot be installed

The workflow builds on a clean runner and caches npm and Gradle but never ~/.android, so a fresh throwaway keystore is generated every run. Handing a volunteer a CI-built APK forces an uninstall. Nothing in the repo warns anyone.

.github/workflows/build_apk.yml · fixed by R1.5

"Visit" meant the wrong thing

The calendar was built as an outbound worklist — volunteers going out to people. The actual primary flow is inbound: supporters phoning to say they are coming, usually for an occasion. Not a code defect, a modelling one, and it reframed the day pane.

found from three phone-call scenarios · fixed by Phase V, G10-R

What gates the release

Seven workstreams and one pilot device is an unacceptable coupling. So the release has a core that must work or nothing ships, and everything else sits behind an independent build-time flag. A pilot failure then costs a flag flip and one rebuild, not a re-plan under time pressure.

Simplified for pilot scale

Three NGOs, and you have offered to walk each through a backup and confirm it restores into the new version. That is a stronger test than the pilot-only check that was planned — a restore rehearsal on real data, on every device. It is accepted, and it buys back five items.

Worth sitting with, because it is the honest answer to "can we simplify". Scaling down process does not shrink defect repair, and every item above is risk-management rather than correctness. No correctness work was cut. The data-model decisions stay exactly as they are — a festival greeting sent on the wrong day is as damaging at three NGOs as at thirty, arguably worse, because these are the relationships the product is being judged on.

Re-entry condition. These five return when either a fourth NGO is onboarded, or any device is upgraded without a human on the call. They are the machinery that substitutes for the person who will not be there — so the debt is repaid on a trigger, not on someone remembering.

Yours, not mine

None of these need me, and the first one is the highest value-per-minute action in the entire plan.

Back up the signing key, off this machine It is the only thing that can upgrade the installed apps. Encrypted, in two places — password manager and an encrypted drive. cp ~/.android/debug.keystore ~/Dnyani_Mitr_SIGNING_KEY_DO_NOT_LOSE.keystore
Treat every existing "file backup" as non-existent Anyone who tapped Backup on a phone and saw "Backup file downloaded" has no file. Ask them to redo it as a WhatsApp text message — that path genuinely works today.
Ask the four laptop users which browser they open the app in One WhatsApp message. Chrome and Edge share storage across file:// pages, which defuses the worst laptop failure. Firefox behaves differently and I will not design around behaviour I have not tested.
Pick the pilot volunteer One reachable person with a real phone and real data, plus one laptop. They upgrade first, and nothing is broadcast until both report clean.
07

What could still go wrong

Phase F cannot be proven by any test. No unit test says anything about how MIUI or ColorOS handle a share intent. It is verified on the pilot phones or it ships switched off — that is the honest limit of what I can promise about it.

There is no downgrade. Android refuses to install a lower version code, so once v3.2.0 lands it cannot be reverted without an uninstall. Recovery is layered instead: switches a volunteer can flip themselves over the phone, and a staged broadcast so a bad release reaches one person rather than everyone.

The rollout has no backup gate. You chose speed over requiring a backup file before sending the APK, and your supervised verification now covers most of that ground. What remains is that the in-app backup nudge ships inside v3.2.0 — so it protects the next upgrade, never this one.

Iteration 10 has never run on a device. Campaigns and notifications are code-verified only. The pilot phone is the first hardware they will ever touch, which is why the digest opt-in is switchable.
